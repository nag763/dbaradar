# Telegram Webhooks Lambda Service - Implementation Plan

**Status**: Plan documented (not yet implemented)  
**Date**: 2026-07-26  
**Service**: `services/webhooks`  
**Technology Stack**: Go 1.26 + Chi v5 + AWS Lambda + API Gateway HTTP API v2

## Executive Summary

This document outlines the complete implementation plan for a new Go Lambda service that receives and processes Telegram webhook requests. The service will handle bot commands (`/add`, `/remove`, `/clear`, `/list`) for subscription management, with rate limiting (50 req/min per IP) and header-based token authentication.

**Key characteristics:**
- **First HTTP endpoint** in the dbaradar project (all existing services are event-driven)
- **Dual-layer rate limiting**: API Gateway throttle + Lambda middleware
- **Two-tier authentication**: API Gateway header validation + Lambda token verification
- **Phase 1 scope**: Echo commands with arguments (foundation for future DynamoDB integration)

## Architecture

### High-Level Data Flow

```
Telegram User (sends /add iphone 15)
         ↓
Telegram Bot API (POSTs to webhook URL)
         ↓
API Gateway HTTP API v2
  ├─ Validates X-Telegram-Bot-Api-Secret-Token header presence
  ├─ Rate limits: 50 requests/minute per IP (X-Forwarded-For)
  └─ Invokes Lambda with APIGatewayV2HTTPRequest
         ↓
Lambda Function (dba-webhooks)
  ├─ Chi adapter converts to http.Request
  ├─ Rate limit middleware (sliding window per IP)
  ├─ Token verification middleware (validates header value)
  ├─ Router matches POST /webhook
  └─ Handler processes command → returns echo response
         ↓
Response returned to Telegram (which sends message to user)
```

### Phase 1: Data Models & Configuration

**Objective**: Define data structures and configuration management

#### 1.1 Go Module (`services/webhooks/go.mod`)
- Initialize new Go module: `github.com/nag763/dbaradar/services/webhooks`
- Pin Go version: 1.26

  - `github.com/go-chi/chi/v5` v5.3.1

#### 1.2 Telegram Data Models (`internal/model/telegram.go`)
**Structures:**
- `Update`: Top-level Telegram webhook event (UpdateID, Message)
- `Message`: Telegram message (MessageID, From, Chat, Date, Text)
- `User`: Telegram user info (ID, FirstName, LastName, Username)
- `Chat`: Telegram chat info (ID, Type, Title, Username)

**Implementation notes:**
- Use JSON tags for unmarshaling: `json:"field_name,omitempty"`
- Only include fields needed for command processing
- Omitempty allows handling incomplete updates gracefully

#### 1.3 Command Models (`internal/model/command.go`)
**Structures:**
- `Command`: Parsed bot command
  - Name: string ("add", "remove", "clear", "list")
  - Arguments: []string (space-separated args)
  - ChatID: int64 (where command was sent)
  - UserID: int64 (who sent it)
  - MessageID: int (for reply reference)

- `CommandResponse`: Response to send back to Telegram
  - Method: "sendMessage"
  - ChatID: int64 (target chat)
  - Text: string (response message)

**Function:**
- `ParseCommand(text string) (*Command, error)`
  - Extract command from message text (e.g., "/add iphone 15" → name="add", args=["iphone", "15"])
  - Validate command is one of: add, remove, clear, list
  - Return error for non-command text or unknown commands

**Test cases:**
- Valid commands: `/add`, `/remove`, `/clear`, `/list`
- With arguments: `/add iphone 15` → args=["iphone", "15"]
- Unknown commands: `/unknown` → error
- Non-command text: `hello world` → error
- Edge cases: multiple spaces, trailing spaces, empty arguments

#### 1.4 Configuration Management (`internal/config/config.go`)
**Structures:**
- `SSMGetter`: Interface for AWS SSM GetParameter (testability)
- `Config`: Contains resolved configuration
  - SecretToken: string (Telegram webhook verification token)

**Function:**
- `Load(ctx context.Context, ssmClient SSMGetter) (*Config, error)`
  - Two-tier resolution:
    1. Check env var `TELEGRAM_SECRET_TOKEN_PARAM` (SSM parameter name)
    2. If set, fetch from SSM with decryption
    3. Fallback to env var `TELEGRAM_SECRET_TOKEN` (direct value)
  - Validate token is not empty
  - Return error if SSM fetch fails

**Test cases:**
- SSM resolution: env var set → fetch from SSM → return value
- Env var fallback: SSM param not set → use direct env var
- Missing token: both empty → error
- SSM error: parameter doesn't exist → error
- Mock SSM with function pointers (no real AWS calls in tests)

### Phase 2: Middleware & HTTP Handlers

**Objective**: Implement rate limiting, authentication, and request handling

#### 2.1 Rate Limiting Middleware (`internal/middleware/ratelimit.go`)

**Structures:**
- `RateLimiter`: Main rate limiter
  - mu: sync.RWMutex (concurrent access)
  - requests: map[string]*bucket (IP → request history)
  - limit: int (50 requests)
  - window: time.Duration (1 minute)

- `bucket`: Request history for single IP
  - timestamps: []time.Time (request times in sliding window)
  - mu: sync.Mutex

**Functions:**
- `NewRateLimiter(limit int, window time.Duration) *RateLimiter`
  - Create rate limiter with specified limits
  - Start cleanup goroutine (remove old entries)

- `(rl *RateLimiter) Middleware() func(http.Handler) http.Handler`
  - Chi middleware factory
  - Extract client IP from X-Forwarded-For header
  - Check if IP has exceeded rate limit
  - Return 429 Too Many Requests if limit exceeded
  - Otherwise, record timestamp and proceed

- `extractIP(r *http.Request) string`
  - Parse X-Forwarded-For header (set by API Gateway)
  - Handle: single IP, multiple IPs (use first)
  - Fallback to RemoteAddr if header missing

**Algorithm:**
- Sliding window: track request timestamps per IP
- On each request: remove timestamps older than window duration
- If remaining timestamps >= limit: reject (429)
- Otherwise: add current timestamp and proceed

**Test cases:**
- Under limit: 49 requests → allow next request
- At limit: 50 requests → allow next (at boundary)
- Over limit: 50 requests within window → reject (429)
- Multiple IPs: each IP tracked independently
- X-Forwarded-For parsing: single IP, multiple IPs, missing
- Sliding window: requests expire after 1 minute
- Concurrent requests: thread-safe (sync.RWMutex)

#### 2.2 Token Verification Middleware (`internal/middleware/auth.go`)

**Constants:**
- `telegramTokenHeader = "X-Telegram-Bot-Api-Secret-Token"`

**Functions:**
- `VerifyTelegramToken(expectedToken string) func(http.Handler) http.Handler`
  - Chi middleware factory
  - Extract header value
  - Compare with expected token
  - Return 401 if invalid or empty
  - Note: API Gateway validates header presence at routing level

- `SkipAuth(next http.Handler) http.Handler`
  - Middleware to bypass token verification
  - Used for health check endpoint
  - Sets context value to skip auth check

**Test cases:**
- Valid token: passes through
- Invalid token: returns 401
- Empty token: returns 401
- SkipAuth: bypasses verification

#### 2.3 HTTP Handlers (`internal/handler/handler.go`)

**Structures:**
- `Handler`: Main request handler
  - logger: *slog.Logger

**Functions:**
- `NewHandler(logger *slog.Logger) *Handler`
  - Create handler with logger dependency

- `(h *Handler) HandleWebhook(w http.ResponseWriter, r *http.Request)`
  - Parse JSON body to Telegram Update
  - Extract message text
  - Parse command using model.ParseCommand
  - Route to appropriate handler (/add, /remove, /clear, /list)
  - Return JSON response with sendMessage method
  - Log: command name, args, chat ID, user ID
  - Errors:
    - 400: Invalid JSON
    - 200: Non-command messages (silently ignore)
    - 500: Processing errors

- `(h *Handler) HandleHealth(w http.ResponseWriter, r *http.Request)`
  - Return 200 OK
  - No auth required (no token verification)

- `(h *Handler) handleAdd(ctx context.Context, cmd *Command) string`
- `(h *Handler) handleRemove(ctx context.Context, cmd *Command) string`
- `(h *Handler) handleClear(ctx context.Context, cmd *Command) string`
- `(h *Handler) handleList(ctx context.Context, cmd *Command) string`
  - Phase 1: Echo command with arguments
  - Format: "Echo /add with args: [iphone 15]"
  - Future: Connect to DynamoDB for actual subscription management

**Test cases:**
- Each command with arguments → 200 + echo response
- Commands without arguments → 200 + echo response
- Invalid JSON body → 400
- Non-command text → 200 (silently ignore)
- Unknown command → 200 (silently ignore)
- Health check → 200 OK

### Phase 3: Router & Lambda Integration

**Objective**: Wire up chi router and integrate with AWS Lambda

#### 3.1 Chi Router Setup (`internal/router/router.go`)

**Function:**
- `New(h *handler.Handler, secretToken string, rateLimiter *middleware.RateLimiter) *chi.Mux`
  - Create chi router
  - Order of middleware matters:
    1. RequestID, RealIP, Recoverer (standard chi)
    2. Rate limiting (must come before auth)
    3. Token verification (rejects early if invalid)
  - Routes:
    - POST /webhook → HandleWebhook
    - GET /health → HandleHealth (with SkipAuth to bypass token check)

**Middleware ordering rationale:**
1. RequestID: Add request ID for tracing
2. RealIP: Extract real client IP
3. Recoverer: Catch panics
4. RateLimiter: Extract IP, enforce rate limit
5. VerifyToken: Validate token value
6. Routes: Handle requests

**Test cases:**
- POST /webhook with valid token → 200
- POST /webhook with invalid token → 401
- POST /webhook without token → 401 (caught by API Gateway validation, but test anyway)
- POST /webhook over rate limit → 429
- GET /webhook → 405 Method Not Allowed
- GET /health → 200 (no auth)
- GET /health over rate limit → 429 (health endpoint still rate-limited)

#### 3.2 Lambda Entrypoint (`cmd/webhooks/main.go`)

**Flow:**
1. Create JSON logger (slog)
2. Load config from SSM (two-tier resolution)
3. Create rate limiter (50 req/min)
4. Create handler
5. Create router (with rate limiter)
6. Create chi Lambda adapter
7. Start Lambda runtime

**Code structure:**
```go
func main() {
    logger := slog.New(slog.NewJSONHandler(...))
    cfg, err := config.Load(context.Background(), nil)
    rateLimiter := middleware.NewRateLimiter(50, time.Minute)
    h := handler.NewHandler(logger)
    r := router.New(h, cfg.SecretToken, rateLimiter)
    adapter := chiadapter.New(r)
    lambda.Start(adapter.ProxyWithContext)
}
```

**Key points:**
- Chi adapter converts APIGatewayV2HTTPRequest ↔ http.Request
- Lambda runtime expects function with signature: `func(context.Context, events.APIGatewayV2HTTPRequest) (events.APIGatewayV2HTTPResponse, error)`
- adapter.ProxyWithContext handles this conversion automatically

## Security Considerations

### Authentication
- **API Gateway**: Validates header presence at routing level (never reaches Lambda if missing)
- **Lambda**: Validates header value (token comparison)
- **SSM**: Token stored as SecureString (encrypted at rest)
- **Environment**: Token passed as SSM parameter name (not value in env var)

### Rate Limiting
- **API Gateway**: Coarse throttling (50 req/min per IP globally)
- **Lambda**: Fine-grained per-IP sliding window rate limiter
- **X-Forwarded-For**: Header set by API Gateway (trusted source)

### Input Validation
- JSON parsing: Reject malformed JSON (400)
- Command parsing: Reject unknown commands (silently)
- Text extraction: Handle missing/empty fields gracefully

### Logging
- Structured JSON logging (no PII in logs by default)
- Command name, arguments, chat ID, user ID logged (non-sensitive)
- Sensitive token never logged

## Key Implementation Notes

### Middleware Ordering
Rate limiter MUST come before auth middleware, so that:
1. Rate limit is checked first (reject over limit regardless of token)
2. Token verification is second (reject invalid token)
3. Prevents attackers from bypassing rate limit with invalid tokens

### Rate Limiter Design
- Sliding window (not fixed buckets) for smooth rate limiting
- Per-IP tracking for fair distribution
- In-memory storage (OK for Lambda, which processes ~1-10 req/min in normal use)
- Background cleanup goroutine prevents memory leak

### Error Responses
- 400: Invalid JSON → genuine client error
- 401: Invalid token → security event (log it)
- 429: Rate limit exceeded → expected under load
- 500: Processing error → Lambda fault (likely bug)

### Logging Strategy
- All errors logged with context (command name, chat ID, IP)
- Structured JSON format (compatible with CloudWatch Insights)
- No sensitive data in logs (token never logged)

### Testing Strategy
- Unit tests mock all external dependencies (SSM, HTTP)
- Integration tests use httptest (no external calls)
- Manual tests verify end-to-end flow after deployment
- Race detector catches concurrency bugs in rate limiter
